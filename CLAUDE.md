# MathNotebook paclet

Paclet for writing math papers in Wolfram notebooks: referencing palette, LaTeX journal stylesheets, LaTeX ↔ notebook conversion, MaTeX integration.

## Layout

- `MathNotebook/` — paclet root: `PacletInfo.wl`, `Kernel/` (Package[] format, loader `MathNotebookLoader.wl`, usage strings in `Usage.wl`), `FrontEnd/Palettes/`, `FrontEnd/StyleSheets/MathNotebook/`, `Assets/`, `Tests/*.wlt`.
- `Scripts/Build*.wls` — generate ALL `.nb` artifacts (stylesheets, palette, tutorial). Never edit generated `.nb` files directly; edit the script and regenerate.
- `Referencing.nb`, `Infrageometry.nb`, `TikZ.nb` — original prototypes, kept as reference; do not modify.

## Conventions

- Conversion functions have pure cores operating on `Notebook` expressions (headless-testable) with thin `NotebookGet`/`NotebookPut` wrappers.
- In the `Package[]` format an **undeclared symbol is private to its own file** (`WolframInstitute`MathNotebook`<File>`PackagePrivate`x`). Calling such a helper from another file creates a distinct, definition-less symbol, so the call just stays unevaluated — **no message, no failure, the operation silently does nothing**. Every cross-file helper needs `PackageScope["name"]` in the file that defines it.
- All four template stylesheets are generated from the same base cell list as `LaTeXBase.nb` and each chains to `Default.nb`; they must define identical style names (enforced by `Tests/StyleSheets.wlt`).
- Palette buttons must be cold-kernel-safe: `Needs["WolframInstitute`MathNotebook`"]` + fully qualified symbols, `Method -> "Queued"`.
- **The TeX importer has two halves with opposite failure modes, and `texToBoxes` needs both.** `ToExpression[tex, TeXForm, HoldComplete]` interprets the TeX as *one Wolfram expression*, so any fragment that is not one — `a, b`, `(V, E)`, `x_1, x_2`, `\begin{cases}…` — answers `$Failed` no matter how ordinary the mathematics is. `Convert`TeX`TeXToBoxes` (the box-producing half `ToExpression` itself calls first, autoloaded, no `Needs`) handles all of those correctly but is presentational: it renders `\mathcal{H}` as an italic `H` and `\ref{k}` as a `CounterBox` spelled out of the letters of "Section". So the expression path stays primary and the box path is its fallback (`presentationBoxes`), with `\ref`/`\eqref`/`\pageref` held at `$Failed`. Also: `ToExpression` answers `HoldComplete[$Failed]` on malformed TeX, which a bare `HoldComplete[expression_]` pattern matches — `MakeBoxes` then renders the literal word `$Failed` into the cell.
- **The document layer (`Document.wl`) round-trips a paper by recording whitespace, not by rules about blocking.** Every cell carries a `"Separator"` tagging rule holding the source whitespace that followed it, and the opening/body/closing indents of an environment are each recorded too, so `ExportLaTeXDocument` is a plain `StringJoin`. Riffling with `"\n\n"` instead was 7 diff lines on one specimen and 38 on the other. Two pattern traps in the same file: a string pattern will **not** take a back-reference to a named `Alternatives` (`name : (a|b) ~~ … ~~ name` answers `StringExpression::invld`, not a non-match), so emit one rule per environment name with the name written literally into both delimiters; and structural delimiters must be anchored to `StartOfLine`, or `%\begin{example}` is matched inside its own comment and a commented-out block becomes a live cell.
- **An imported `\ref` is a bare `CounterBox` chain, not `citationButton`.** LaTeX authors write the word themselves (`Theorem~\ref{Thm:2}`), so the palette's prefix would say it twice; `\eqref` is the same chain in parentheses, and which command it was is recovered on export from whether the box is parenthesised. Numbering only works under a MathNotebook stylesheet — the counter lives in `CounterIncrements` on the style — so on `Default.nb` a definition reference renders `2.0`, which looks like a broken reference and is not one. Any front-end test of numbering must install the sheet.
- **A `.bib` bibliography's `Reference` cells emit nothing into the `.tex`.** The entries are not in the source — it says `\bibliography{refs}` — so the block's **last** cell carries those commands verbatim and every earlier one carries a `"Suppressed"` tagging rule that `notebookToLaTeX` filters out. Two consequences: the `.bib` stays the source of truth, so editing an entry in the notebook does not reach the `.tex`; and no round trip can detect whether the bibliography renders at all, which is why the assertion lives in `Tests/FrontEnd.wlt`. A `\cite`, by contrast, converts **unconditionally** where T3's `\ref` needs a target cell — a citation's label is literal text (`referenceLabel`'s `[key]`, the same string the entry's dingbat shows) and is right with no bibliography, where a `CounterBox` would render `XXX`.
- **A `.bib` field cannot be found by a string pattern**: a value holds both the comma that separates fields and the braces that end the entry (`title={A first paper, with a comma}`). `Accumulate` over the brace characters gives the depths in one pass — cut at the commas at depth 0, stop where the depth first reaches −1. Also, six named characters such a parser wants do not exist (`\[NAcute]`, `\[SAcute]`, `\[ZAcute]`, `\[IBar]`, `\[OBar]`, `\[UBar]` print as their own literal name) while their neighbours do; sweep an accent table in the kernel rather than inferring it.
- **A `figure` is the caption plus the code that draws the picture.** The caption becomes a `Caption` cell the notebook owns and writes back, and the rest of the environment's source — `[htpb]`, `\centering`, the `\includegraphics` options, a whole `tikzpicture` — rides verbatim in a `"FigurePrefix"` rule with everything after the caption in `"Trailing"`, where `labelledCell` finds the `\label` as it does for a section. That is how TikZ survives a round trip the notebook cannot render. Each `\includegraphics` becomes an `Input` cell holding `Import[FileNameJoin[{NotebookDirectory[], file}]]`, to be replaced with the code that *generates* the picture; the whole evaluation family (`Input`, `Output`, `Code`, `Print`, `Message`, `Echo`) emits nothing into the `.tex`, so a live figure cannot leak into the source — and equally, the generating code never reaches it. A captionless figure owns nothing and re-emits from `"FigureTeX"`. Figures number from the `Caption` counter straight through the document, as `article` does.
- **A byte-identical round trip measured in one kernel does not survive a file.** Saving a notebook and opening it again splits a `ButtonBox[RowBox[…]]` inside a `TextData` into one button per run — this is not only `NotebookWrite` — so every imported citation and cross-reference came back multiplied: 14 buttons became 46 on the specimen, `\cite{a, b}` exported five `\cite` commands, and `\eqref{k}` came back as `\cite{k}\ref{k}\cite{k}` because the parentheses had been carried off into buttons of their own. `mergedButtons` in `Document.wl` rejoins consecutive buttons on one key before anything reads them. Any fidelity claim about a notebook must go through `Export`/`NotebookOpen`/`NotebookGet` at least once. The same reopen also **groups** cells into `CellGroupData` — harmless, since `notebookCellList` flattens, but a naive `Cases[…, Cell[_, style_String, ___]]` on a reopened notebook then reports almost nothing.
- **`NotebookEvaluate` inside `UsingFrontEnd` hangs**: the front end's evaluator is the kernel driving it. Put an `Output` cell in kernel-side with `ToBoxes` instead — cheaper, and the assertion is the same. (Relatedly, `Cases` on a `Notebook` defaults to level 1, where the only elements are the cell *list* and the options.)
- **In a string pattern `~~` binds loosest and `:` tightest**, so `optional : ( … ) | "" ~~ rest` is `StringExpression[Pattern[optional, Alternatives[…, ""]], rest]`, not an `Alternatives` over the whole pattern as it reads.
- **`First @ StringCases[s, rule, default]` is a silent bug** — the default lands inside `StringCases` as the match count, the call returns unevaluated, and a `Module` destructuring downstream leaves symbolic values with no message. Always `First[ StringCases[...], default ]`.
- **A TeX letter the kernel has a value for is a third failure mode of the expression path**, alongside "not one expression" and "malformed". `ToExpression["E", TeXForm]` is Euler's number and `"I"` is the imaginary unit, so `texToBoxes` returned `"\[ExponentialE]"` / `"\[ImaginaryI]"` — the wrong glyph, not a blank, and silently. Sweeping `a`–`z`, `A`–`Z`: those two and no others. Such a parse is treated as a misread and handed to `presentationBoxes`, which is right about all of them. Two traps: in a pattern `E | I` is `Alternatives[E, Complex[0, 1]]` — `I` evaluates, `E` does not — so it fixes `E` and silently misses `I`; both need `HoldPattern`. And `\[ExponentialE]` is U+F74D, a private-use character a terminal prints as nothing, so `Print`/`InputForm` report a wrong glyph as an empty one — read it with `ToCharacterCode`.
- **A converted cell can become several cells.** Display math is normally written glued into a paragraph — `\begin{equation*}` on the line after the prose, no blank line anywhere — and it has to be lifted into its own `DisplayFormula` cell, so `convertLaTeXCell` may answer with a list and `mapCells` flattens. One delimiter table (`$displayDelimiters`) generates both the anchored whole-cell rules (`displayParse`) and the unanchored split rules (`splitDisplayMath`), so the two halves cannot disagree about which environments exist; `Shortest` in the unanchored rules is what stops two environments in one paragraph matching as a single span. The consequence for any round trip: the pieces are source-verbatim but the paragraph blocking is not, and the join that restores it is a single `"\n"`, not `"\n\n"`.
- **An equation number is invisible to a single-cell `Rasterize`.** `DisplayFormula` and `DisplayFormulaNumbered` on the same body measure identical ink (243 for `x^2+y^2=z^2`), because the number is a `CounterBox` — the same reason a tagged counter reads `XXX`. Rendering the whole notebook separates them (1268 unnumbered against 1368 numbered), which is the only way to assert "unnumbered" as a display fact rather than as a style name.
- **Round-trip fidelity cannot detect a display defect.** The exporters read the stored `"SourceTeX"` tagging rule, not the boxes, so a cell that renders as a blank still round-trips byte-identically. Display has to be asserted separately; rasterized **ink area** works headless and is well separated (`Blank < Converted < Literal` measured 390 / 575 / 703 for an inline `$(V, E)$`, the middle one having lost the two `$` glyphs).
- **A `CellDingbat` cannot read the options of the cell it labels.** `CellDingbat -> Cell[BoxData[ToBoxes @ Dynamic[... CurrentValue[EvaluationCell[], CellTags] ...]]]` renders, and renders empty: inside the dingbat `EvaluationCell[]` does not resolve to the owning cell. A label that depends on the cell's own tags has to be written into the cell (`referenceDingbat` in `Referencing.wl`), not derived at display time. Counters are the exception — `CounterBox` is a front-end box and works in a dingbat, which is how the theorem environments number themselves.
- **`CounterBox[counter, tag]` resolves the counter at the cell tagged `tag`, not at the box's own position** — the front end's native cross-reference, needing no kernel, correct in the PDF, and renumbering itself when cells move. It is what a citation to a numbered environment is built from (`citationButton[tag, style]` in `Referencing.wl`). An unknown tag renders `XXX`, so the *style* is resolved at insert time and a tag no cell carries falls back to `[tag]`. `CopyCellReference` cannot share it: that button is keyed on a `CellID`, and the second argument must be a tag.
- **`Rasterize` on a single cell strips document context**: every `CounterBox` in it reads 0 and every tagged one reads `XXX`. To see a counter, render the whole notebook — `Export[file, notebookObject]`.
- `NotebookWrite` of a whole `Cell[TextData[...]]` splits a `ButtonBox[RowBox[...]]` into one button per run; writing the bare `ButtonBox` at a selection point leaves it intact. Both render the same, but only the inline form round-trips.

## Palette state and folding

- Palette state persists **despite `Saveable -> False`**: the front end saves a palette's own `TaggingRules` in `$UserBaseDirectory/FrontEnd/init.m` under `CurrentValue[$FrontEnd, PalettesMenuSettings]`, keyed by palette file name. Write state on `EvaluationNotebook[]` under a flat key, as the built-in palettes do; do not use `$FrontEnd` tagging rules.
- `CurrentValue[EvaluationNotebook[], {TaggingRules, key}, True]` is fully front-end-side — no kernel is launched to display or fold the palette. Set it from an `EventHandler` with `Method -> "Preemptive"`, and use two handlers (set `True` / set `False`) rather than a `Not`.
- `PaneSelector` reserves the size of its **largest** pane unless given `ImageSize -> Automatic` explicitly. Without that option a collapsed group still occupies its open height and the fold does nothing.
- `Rasterize` renders `Dynamic` as a placeholder and `PaneSelectorBox` at max size, so a raster can neither show nor measure fold state. Build a separate static rendition for screenshots (`Scripts/BuildPalette.wls` has `staticGroup` beside `paletteGroup`).
- Never `Import` **or `Get`** a palette `.nb` into a variable to inspect it — the result is re-evaluated, so a literal `EvaluationNotebook[]` becomes `$Failed` and every `CurrentValue` collapses to its default, reporting one window size for every fold state. Read it as text, or measure via `AbsoluteCurrentValue[nb, WindowSize]` after `NotebookOpen`.
- To measure a fold state, patch the palette's **existing** `TaggingRules` option as text — the generated file already carries one (an all-`True` association the exporting front end writes), a second copy of the option is ignored, and the association spans several lines, so the regex needs `(?s)`: WL's `RegularExpression` `.` does not cross a newline.

## Style overrides on a document

`View.wl` ships **two** controls, both font sizes: `SetDocumentFontSize` and `SetMathFontSize`, cleared by `ResetDocumentView`. A third, `SetContentWidth`, shipped in 0.1.5–0.1.7 and was **withdrawn in 0.1.8** at Pavel's call — a content column is not wanted in any form, relative or absolute. The cell-margin and paper-geometry notes below are kept because they were expensive to establish and they describe the front end, not that control; do not read them as describing shipped code. `ResetDocumentView` still clears the old `"ContentWidth"` tagging rule so documents written with those versions are left clean.

- The `"Printout"` variant of a style wins over the bare style name **across the whole stylesheet chain**. Since `LaTeXBase` sets an explicit `FontSize` on every prose/math style's `"Printout"` variant, an override written only on the bare name changes the screen and leaves the PDF byte-identical. Always write both.
- `CurrentValue[nb, {StyleDefinitions, style, option}] = value` is silently ignored. Build the private sheet (`Notebook[{Cell[StyleData[StyleDefinitions -> parent]], overrides...}, StyleDefinitions -> "PrivateStylesheetFormatting.nb"]`) and install it with `SetOptions`.
- **Reading** that same path *does* work, and resolves through the whole chain — including styles no MathNotebook sheet declares (the `Item` family, which comes from `Default.nb`) and a document still on `Default.nb`. It is the way to get a style's base geometry; read it off a scratch notebook created with the *parent* sheet, or a second call compounds its own override.
- To read the **print** value, put the environment in the path as a list: `CurrentValue[nb, {StyleDefinitions, {"Theorem", "Printout"}, FontSize}]` returns 10 where the bare path returns 13. `StyleData[style, "Printout"]` in that position does **not** work — it silently returns the screen value, so every printout override gets written at its screen size. Filter the results for `NumericQ`: `Default.nb` resolves `DisplayFormulaEquationNumber` to the symbolic `-1 + Inherited`.
- Read the *list* of styles to touch from `LaTeXBase.nb`, not from the chain. The chain happily resolves a size for the character styles (`Hyperlink`, `Citation`, `URL`) too, and pinning those stops an inline citation from inheriting the size of the cell it sits in.
- **`Scaled` in `CellMargins` always resolves against the window, in print as much as on screen** — never against the paper. Measured: a bare `Scaled[0.2]` in the `"Printout"` variant put the left ink at 174 on *both* 612 pt and 842 pt paper. So on screen `Scaled[0.5] - width/2` on both sides is exactly an absolute centered column that tracks a window resize, and in print the same expression is meaningless. Earlier sessions recorded both halves of this wrongly (T4 read a `Scaled` print inset as tracking the printable width, T6 read the sum form as the broken case); the sum is fine, the environment is what differs.
- **A printout cell margin is laid out at 0.72 and only then put on the paper.** `Default.nb` gives `Cell[StyleData[All, "Printout"]]` a `Magnification -> 0.72`, so a printed margin is `0.72 ×` its value, measured in from that edge's `PrintingMargins`. An absolute column of `w` points on paper is therefore the point margin `(printable - w) / (2 × 0.72)` — verified to the point at 200, 300 and 400 pt on two papers. Reading the 0.72: `AbsoluteCurrentValue[nb, Magnification]` on a scratch document created with `ScreenStyleEnvironment -> "Printout"`. The obvious path, `CurrentValue[nb, {StyleDefinitions, {style, "Printout"}, Magnification}]`, silently answers 1.
- Printable width is `First @ CurrentValue[nb, {PrintingOptions, "PaperSize"}] - Total @ First @ CurrentValue[nb, {PrintingOptions, "PrintingMargins"}]`; the template sheets declare A4 with 72 pt margins, so it is 451.28.
- `PageWidth -> w` in a style *is* absolute (identical ink `{102, 252}` on both papers) but left-aligns at the style's own margin, and combining it with symmetric `Scaled` margins fights — `Scaled` then resolves against the style's own `PageWidth`, and the two together collapsed the block to 73 pt and were not centered.
- Measuring an exported PDF: run the page headers and footers off (`PageHeaders`/`PageFooters -> {{None, None, None}, ...}`) or their own margins widen the ink column, and trust only the **left** ink edge — prose is ragged right, so the right edge lands wherever the longest line happens to end.
- Headless verification trap: a private sheet whose parent is an **embedded** notebook (`Cell[StyleData[StyleDefinitions -> Get[path]]]`) applies your own override cells but lets every *unoverridden* style fall through to `Default.nb` instead of the intended parent. Styles you wrote read correctly while styles you did not read Default's values, which looks exactly like a leaking control. Only the document-level `StyleDefinitions -> Get[path]` form resolves properly.
- That trap reaches **notebook options too, not just styles**: with an embedded parent, `CurrentValue[nb, {PrintingOptions, "PaperSize"}]` answers `Automatic`, so anything computed from the paper becomes symbolic and the printed result is silently garbage. It also means a headless PDF export uses `Default.nb`'s 54 pt printing margins while a read taken before the wrap reports the sheet's own 72 — the two disagree by exactly the amount that makes an absolute column look wrong. Read paper geometry only off the **bare parent**: restore `StyleDefinitions -> parent` first, read, then install the private sheet.
- **Never stage a stylesheet into `$UserBaseDirectory/SystemFiles/FrontEnd/StyleSheets/`** to make a sheet resolve by name in a script. It does resolve — and then *every* subsequent front end launch on the machine hangs indefinitely, including unrelated builds, until the directory is removed. Cost two wedged sessions and a round of killed kernels to find. Embed the sheet instead and accept the trap above.
- A style declared `StyleData[name, StyleDefinitions -> StyleData["Text"]]` — the theorem environments, `Proof`, `Reference`, `Author`, `Date` — does **not** pick up a child sheet's override of `Text`; the inheritance is resolved inside the parent. Such a style carries no bare `FontSize` of its own, so an override generated from the base sheet's declared sizes skips it and its size never changes on screen.
- `CellMargins` accepts `Scaled[fraction] + points`, and the front end resolves the sum (`Scaled[a] + Scaled[b]` behaves as `Scaled[a + b]`). A symmetric `Scaled[0.5] - width/2` is therefore an absolute on-screen column, and a per-style point offset added to it keeps each style's own indent — section numbers and theorem dingbats are drawn to the left of their own cell margin. Anchor such offsets on `Text` so the *body* ends up centered; anchoring on the smallest margin centers the hull and leaves the body visibly off-centre (measured 11.5 pt on a 340 pt column). The offsets are then negative, so a printed inset has to be clamped at the widest hang or a section number falls off the paper.
- Of two `StyleData` cells for the same name and environment in one sheet, the **first wins and the second is discarded whole** — its options are not merged in, so an option written only in the second never applies and silently falls back to the parent (measured both for the same option twice and for two different options). Emit exactly one cell per style and environment, carrying every option; never append a second. This is why `View.wl` runs its generated cells through `mergedStyleCells`, and it is the trap that made the withdrawn width control a silent no-op on every style that also carried a size.
- The front end **drops `TaggingRules` from a private stylesheet notebook** — string, rule list or association alike — while adding `Visible` and `FrontEndVersion` of its own. To recognise a sheet you generated, mark it with a hidden cell (`Cell[StyleData["<marker>"], StyleMenuListing -> None, MenuSortingValue -> None]`); cells survive the round trip. Without a marker each install nests the previous sheet inside the new one and reset can no longer recover the real parent.
- Reset = recover the parent with `FirstCase[..., Cell[StyleData[StyleDefinitions -> name_]] :> name]` and assign it back verbatim — it is a string from the menus but a `FrontEnd`FileName` from the palette.
- `Magnification` never reaches print; it is not a font-size control.
- Headless testing: `"MathNotebook/AMSArticle.nb"` and `FrontEnd`FileName[...]` have both been seen to fall back to `Default.nb` silently in a `wolframscript` run with the paclet installed. What always works is embedding the sheet: `StyleDefinitions -> Get[<absolute path to AMSArticle.nb>]`. Assert the sheet loaded (`CurrentValue[nb, {StyleDefinitions, "Title", FontSize}]` is 26, not 45) before trusting any measurement — that assertion is the point, not the resolution method.
- That fallback is **not** unconditional, and the earlier note that the service front end never sees a freshly installed paclet's `FrontEnd` extension is wrong. Measured with no MathNotebook installed at all, `FrontEnd`FileName[{"MathNotebook"}, "AMSArticle.nb"]` gives Title 45; after `PacletInstall` from the cloud plus ``FrontEndExecute[FrontEnd`ResetMenusPacket[{Automatic, Automatic}]]`` **in the same `UsingFrontEnd` session** it gives 26, as does a front end launched after the install. So the menu reset really does make new stylesheets live, and a stale read means stale paclet data, not an incapable service front end.

## Publishing

- `Scripts/PublishPaclet.wls` owns publishing: it stages `PacletInfo.wl` + `Kernel/` + `FrontEnd/` + `Assets/` + `Tests/` + `Documentation/` (each only if present), archives, uploads to `MathNotebook.paclet`, and only then writes the version marker `MathNotebook-version.txt` — archive first, so a failed upload never leaves the marker promising a version that is not there. It is still the canonical publisher because of that ordering and the version marker; the generic `publish-paclet`/`build-paclet` recipe no longer drops the palette and stylesheets (it stages every top-level item as of plugin 4.2.0) but it knows nothing about the marker.
- The 21 reference pages are deployed publicly at `https://www.wolframcloud.com/obj/hajek_pavel/MathNotebook/Documentation/index.html` (one cloud notebook per symbol under `Documentation/ref/`, plus an HTML index), for readers who have not installed the paclet. Regenerate with the plugin's `deploy_paclet_docs.wl`; the pages' `paclet:` links are rewritten to the deployed siblings, since a paclet URI resolves to nothing outside the Documentation Center.
- The cloud URLs live once, as `PackageScope` symbols in `Kernel/Update.wl`; the script reads them off the loaded paclet and aborts if they are not strings (a `PackageScope` symbol referenced from outside silently exists with no value — the trap in *Conventions*). `MATHNOTEBOOK_PACLET_URL` / `MATHNOTEBOOK_VERSION_URL` override both for a staging dry run.
- `$CloudBase` is `None` in `wolframscript`, so `CloudConnect[]` fails there with `invbase` — set it to `https://www.wolframcloud.com` first. The MCP kernel is already connected.
- `URLRead[request, {"StatusCode", "Body"}]` returns an **Association**, not a list; match it with `KeyValuePattern`.
- A cloud object read back **immediately** after `CloudExport` came back unreachable once and read correctly a minute later (the cloud serves `cache-control: public, max-age=60`). Do not treat a single failed read right after publishing as a broken marker. The same caching makes two reads of one marker seconds apart disagree — a probe must read once and bind, never call `cloudVersion` twice and compare.
- Versions compare only as padded integer lists (`PadRight[ToExpression @ StringSplit[v, "."], 4]`); as strings `"0.1.12"` sorts before `"0.1.9"`. `Order[a, b]` is `-1` when `a` sorts **after** `b`, so "the cloud is newer" is `Order[cloudList, installedList] === -1`.
- `UpdateMathNotebook[]` needs a front end — `Notebooks[]`, `MessageDialog` and `FrontEndExecute` all fail in a bare `wolframscript` kernel. They do **not** fail inside `UsingFrontEnd[...]`, so the whole install path *is* drivable headless: wrap `installUpdate` in `UsingFrontEnd`, having first `NotebookOpen`ed the palette `Visible -> False` so `reopenPalette` has something to close. Only the `MessageDialog` in the exported wrapper is left untested that way. Its decision core (`updateAction`, `updateMessage`) is pure and is what the `.wlt` tests cover.
- A file-private helper is reachable from a probe by its full name — `Symbol["WolframInstitute`MathNotebook`Update`PackagePrivate`installUpdate"]` — which is how the install path gets exercised without giving it a `PackageScope` it does not otherwise need.
- Run `Scripts/*.wls` with `wolframscript -file`, never `-code` + `Get`. Under `-code` the scripts' `$ScriptCommandLine` is non-empty but meaningless, so it matches their `{path_, ___}` branch, the `MATHNOTEBOOK_REPO` fallback never fires, and the repo root comes out as something like `/private` — `DeployPreviews.wls` then cheerfully published four samples with `$Failed` stylesheets. `DeployPreviews.wls` now sets `$CloudBase`/`CloudConnect[]` itself so `-file` is always enough.

## Build & test

- Tests: `wolframscript -file run_tests.wls`, or `TestReport` over `MathNotebook/Tests/*.wlt` after `PacletDirectoryLoad`.
- Every `.wlt` but one is kernel-only and stubs its chain reads. `Tests/FrontEnd.wlt` is the exception and exists because unit tests passed while both `ViewAndReferenceDefects` bugs shipped: it measures resolved sizes and tag-resolved styles through a real front end. It does all its measuring in a single `UsingFrontEnd` up front so the `VerificationTest`s stay pure comparisons — otherwise one front-end problem fails every test with a message storm. When changing `View.wl` or `Referencing.wl`, check a test still bites by **reintroducing the defect**, not by watching it pass; the kernel-only files stay green through a broken `citationTargetStyle`.
- That check is worthless until you confirm the patch landed: a `perl -pi` that silently matches nothing leaves the suite green, which reads exactly like "the test does not bite". Print the changed line before believing the result.
- Build/install: temp copy → `CreatePacletArchive` → `PacletInstall[..., ForceVersionInstall -> True]` (build-paclet skill).
- After first install, front end menus need a restart or ``FrontEndExecute[FrontEnd`ResetMenusPacket[{Automatic, Automatic}]]``.
